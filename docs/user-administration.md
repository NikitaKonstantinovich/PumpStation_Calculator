# Уровни доступа и пользователи

В опубликованной базе `44b9f38` уровни — `user` и `admin`, обычная
регистрация создаёт `user`. В локальной рабочей копии отображаются
`base`, `plus`, `pro`, `admin`, а регистрация создаёт `base`. Переданный
с клиента уровень не учитывается в обеих версиях.
См. [версии инструкций](README.md). Только `admin` видит пункт «Список пользователей» и имеет
доступ к `GET`, `POST`, `PATCH /api/users`. Прямой переход на
`/?view=users` не открывает список обычному пользователю.

## Локальное расширение уровней доступа

Таблица и ограничения до следующего раздела относятся к рабочей копии
с миграцией `0010`; в опубликованной базе `44b9f38` их нет.

| Уровень | Настройки проекта | Исполнение DN и коллекторов |
| --- | --- | --- |
| `base` | Только значения по умолчанию | Автоматический подбор |
| `plus` | Можно менять только блок «Опции» | Автоматический подбор |
| `pro` | Все настройки, включая тип установки, входной напор, курсы и скидки | Ручные изменения доступны |
| `admin` | Все возможности `pro`, плюс управление пользователями и расчёт комплектующих | Ручные изменения доступны |

Рабочая точка подбора (расход, напор, количество насосов), выбор насоса,
свои проекты и оформление интерфейса доступны на всех уровнях.
Для `base` и `plus` ручные DN, PN, материал, соединения, патрубки,
межосевые расстояния и эксцентрическое исполнение коллекторов закрыты.
Сервер проверяет права при сохранении проекта и при запросах расчёта/создания/
обновления коллектора. Подмена JSON не даёт доступа к этим параметрам.
Импорт и открытие проекта с недоступными настройками отклоняются с объяснением.
Исходный сохранённый проект не сбрасывается и не перезаписывается; при начальной
загрузке вместо недоступного проекта открывается новый стандартный проект.

## Общие действия администратора

Таблица пользователей содержит почту, имя, уровень, скрытый пароль и статус присутствия.
Доступны поиск, ручное обновление, создание и редактирование аккаунтов.
Перед записью интерфейс показывает изменяемые поля в формате «Было / Станет».
Отмена и возврат в форму ничего не записывают. При конфликте версий нужно
закрыть окно, обновить список и повторно проверить изменения.

Пароли хранятся только в виде PBKDF2-хеша; API не возвращает ни пароль,
ни хеш. Администратор задаёт новый пароль от 10 до 256 символов.
Пустой пароль при редактировании сохраняет существующий. Созданный вручную
пользователь может войти сразу, без письма подтверждения; администратор
должен проверить правильность адреса перед созданием.

Смена почты, пароля или уровня завершает все сессии изменяемого аккаунта
и аннулирует неиспользованные ссылки подтверждения/сброса. Изменение только
имени сохраняет сессии. При изменении собственных учётных данных потребуется
повторный вход. Понизить собственный уровень `admin` нельзя, это должен
сделать другой администратор.

## Присутствие

Открытое приложение отправляет авторизованный сигнал каждые 30 секунд и
при возврате на вкладку. «В сети» означает, что есть хотя бы одна неистёкшая
сессия с сигналом за последние 2 минуты. Закрытие браузера, потеря связи
или приостановка фоновой вкладки отразятся после этого интервала. Выход
удаляет текущую сессию; другие активные устройства продолжают учитываться.
Список пользователей обновляется каждые 30 секунд.

## Обновление базы

Схема дополнена полями `users.role`, `users.revision`, `sessions.last_seen_at`.
Миграция — `drizzle/0007_user_administration.sql`. API авторизации также
проверяет эти поля и добавляет недостающие при запуске старой локальной базы.
Не применяйте SQL-миграцию повторно, если эти поля уже созданы API.
В локальном расширении миграция `0010_user_access_levels.sql` добавляет
`users.access_level`; опубликованная база заканчивается на `0007`.
Прежние `user` получают `pro`, сохраняя доступ и данные. Новые аккаунты получают
`base`; `admin` остаются администраторами. API авторизации выполняет такое же
обновление старой локальной схемы. Если поле уже создано API, SQL повторно не
применяйте. Таблица пользователей не пересоздаётся: внешние ключи, проекты,
пароли и сессии сохраняются. Внутреннее поле `role` остаётся `admin/user` ради
совместимости со старым CHECK; API возвращает `admin` или значение `access_level`.
Автоматического назначения первого зарегистрировавшегося администратором нет.

Для назначения администратора существующему аккаунту **локальной** D1:

```powershell
python scripts/set-local-admin.py --email account@example.com
```

Скрипт проверяет однозначность базы и аккаунта, создаёт резервную копию
в `.wrangler/backups/`, добавляет недостающие `role`, `revision`,
`sessions.last_seen_at` и назначает `role=admin`. Скрипт не создаёт
`access_level`: в локальной ветке это поле добавляют миграция `0010`
или API авторизации.
Почта и пароль аккаунта не изменяются. Новых аккаунтов скрипт не создаёт.
Локальная база и опубликованный сайт независимы: запуск скрипта или
передача исходников в Git не меняют production D1.

## Проверка

В опубликованной базе используйте `node --test tests/users.test.mjs`.
В локальной ветке дополнительно доступен `tests/project-access.test.mjs`:
`node --test tests/users.test.mjs tests/project-access.test.mjs`.
Эти проверки используют SQLite с транзакциями
D1: ограничение доступа, обновление старой схемы, присутствие, подтверждение,
валидацию, дубли почты, хеширование, вход созданного аккаунта, конфликты
версий, отзыв сессий, запрет самостоятельного понижения уровня, переход старых
аккаунтов на `pro`, ограничения сохранения/импорта проектов и исполнения коллекторов.
