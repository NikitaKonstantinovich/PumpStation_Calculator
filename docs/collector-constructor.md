# Конструктор коллекторов

Инструмент `collectors` доступен в списке рабочего пространства. Используется
общая инфраструктура свободных окон, мобильного режима, сетки, сворачивания и
отдельных вкладок. В `DEFAULT_PANELS` он не добавлен. Две карточки отображаются
одновременно; число колонок зависит от ширины панели.

## Изменённые и добавленные файлы

- `app/page.tsx`, `app/globals.css`: подключение панели, отображение и синхронизация.
- `app/project-config.ts`: PanelKind, SpecOption, состояние проекта и нормализация.
- `app/dn-defaults.ts`: общие существующие рекомендации DN для обоих инструментов.
- `app/collector-calculations.ts`: чистые расчётные функции и типы BOM.
- `app/collector-project.ts`: рекомендации, ручные значения, инвалидация и спецификация.
- `app/collector-constructor.tsx`: карточки и обращения к API.
- `app/collector-catalog.ts`: преобразование существующего каталога без подстановки цен.
- `app/collector-catalog-server.ts`: чтение актуального импорта D1.
- `app/api/collectors/route.ts`: защищённые операции чтения, расчёта и записи.
- `db/schema.ts`, `drizzle/0005_collectors.sql`, `drizzle/meta/0005_snapshot.json`,

- `scripts/build-collector-catalog.mjs`, `public/collector-catalog.json`,

- `tests/collectors.test.mjs`, `tests/load-ts.mjs`, `tests/rendered-html.test.mjs`:
  расчётные, интеграционные и обновлённые регрессионные проверки.

## Модель данных

Проект сохраняет `station-collectors`, содержащую независимые `suction` и
`discharge`. Каждая карточка хранит снимок `DnEntity`, рекомендации, ручные
переопределения, S1/S2, эксцентриситет, итоговую конфигурацию, код, геометрию,
скорости, состав, сварку, результат расчёта, версию каталога и найденную запись
базы. Это часть обычного JSON проекта и сохраняется существующим API проектов
в D1, а также экспортируется в файл.

`collectors` хранит уникальный точный код, тип, JSON конфигурации и расчёта,
сохранённую цену, дату её обновления, длину и стоимость сварки, источник и автора.
`collector_items` хранит строки состава с устойчивой ролью, исходным ID
компонента, количеством, единицей, ценой, стоимостью и происхождением данных.
Деньги в SQL записываются в миллионных долях рубля, как в существующей базе.
Состав и заголовок записываются одной транзакцией D1 `batch`.

Миграции 0000–0004 сохранены. Миграция 0005 содержит только две новые таблицы
и их индексы. Снимок 0005 также отражает существующие таблицы шкафов, которые
ранее были добавлены SQL-миграциями без отдельных снимков. Повторного создания
таблиц шкафов в SQL 0005 нет. Миграцию следует применить штатным процессом
развёртывания D1 перед использованием новой базы; API не создаёт её при запросе.

## Источники и расчёты

DN патрубков берутся из `suctionValveDn` / `dischargeValveDn` и соответствующих
`secondary*` полей. DN общего коллектора первоначально выбирается как больший
из рекомендаций активных контуров. Если поля пусты, используются те же функции
автоподбора, что в инструменте DN. Соединения, PN и материал берутся из `DnEntity`;
стандарт материала зависит от типа станции. SettingsEntity уже содержит
`combinedCircuitsSimultaneous`; дополнительного переключателя нет.

Количество патрубков равно рабочим плюс резервным насосам. Расход — Q1 для
одного контура, max(Q1,Q2) для совмещённой станции с раздельной работой и пожарной
станции с жокеем, Q1+Q2 только для одновременной работы совмещённых контуров.
Резерв не увеличивает расход. Скорость патрубка использует Q контура / число
рабочих насосов, а скорость коллектора — общий расчётный расход.

L = N1×S1 + N2×S2. Длина каждого патрубка = 0,5×наружный Ø коллектора +
1,1×L болта. L болта импортируется из «Полезная инфа»!P51:R70, таблицы соединения
двух фланцев, с сохранением адреса ячейки. Наружный диаметр трубы и толщина
берутся из каталога; внутренний диаметр = наружный − 2×толщина. DN в эти
формулы как физический диаметр не подставляется. Для сгонов DN15/DN20 наружный
диаметр берётся из таблицы труб соответствующего материала того же калькулятора.

Сварка: по 2πD на каждый приварной концевой фланец или воротник, по 2πD на
насосный фланец/воротник, по 1,4πD на каждую врезку патрубка и по πD на каждый
сгон. Везде учитывается реальное количество. Длина в мм переводится в метры;
тарифы — 5000 ₽/м для AISI304 и 2400 ₽/м для СТ20.

Фланцевое подключение к сети даёт ровно два фланца. На каждый фланцевый
патрубок приходится один фланец. Для AISI304 при DN≤200 и PN<25 добавляется
также воротник; иначе используется приварной фланец. В свободном фланцевом
комплекте шов считается на воротнике один раз. При резьбе фланцев нет.
Всасывание содержит один сгон DN15 с заглушкой; напор — два DN15 и один DN20.
Крепёж отсутствует в составе и стоимости коллекторов; общие позиции крепежа
спецификации сохраняются.

Цена равна сумме количеств × цен всех компонентов и сварки. Для труб берётся
именно цена за метр, а не цена за тонну или килограмм. При активном импорте D1
используются `components`, `component_attribute_values`, `component_prices` и
связанные таблицы. При отсутствии активного импорта используется поставляемый
снимок `binding-components.json`. Ошибка SQL не подменяется снимком. Версия
каталога зависит от его содержимого, поэтому изменения цен инвалидируют расчёт.

## API и спецификация

- `GET /api/collectors?code=…`: поиск по точному каноническому коду.
- `GET /api/collectors?catalog=1`: актуальные компоненты и расчётные справочники.
- `POST /api/collectors`, action `calculate`: серверный расчёт.
- action `create`: явное создание полностью рассчитанного изделия.
- action `refresh`: повторный расчёт и атомарное обновление цены, BOM и даты.

Все операции используют существующую авторизацию `currentUser`. Клиентская
цена и клиентский BOM не принимаются за источник расчёта. Некорректная резьба,
эксцентрический напорный коллектор и неполный расчёт не записываются.

Спецификация использует `suctionCollector` (03.01) и `dischargeCollector` (04.02).
Старые стандартные названия преобразуются в эти идентификаторы. Изменения
обновляют строки без дублирования. Найденное изделие имеет статус `selected` и
цену базы; полный несохранённый расчёт — `confirmation`; отсутствие или
устаревание расчёта — `clarify` без прежней расчётной цены. Ручные DN сохраняются
при изменениях рекомендаций и сбрасываются только действием пользователя.

## Проверки и ограничения

`node --test tests/*.test.mjs` проверяет все 20 заданных случаев, формулы скоростей
и сварки, версию каталога, полный набор SQL-миграций, авторизацию API, точность
поиска, уникальность кода, повторное обновление BOM и чтение изменённых цен D1.
Для полного расчёта в тестах используются явно обозначенные фиктивные
комплектующие; они не входят в производственный каталог.

В текущем каталоге отсутствуют резьбовые заглушки DN15/DN20 нужных материалов.
Также для AISI304 большого DN отсутствуют отдельные приварные исполнения PN10/16.
Поэтому реальные конфигурации могут оставаться неполными: интерфейс показывает
конкретные отсутствующие позиции, размеры и цены, а запись в базу блокируется.
Цены и изделия из другого материала или PN не подставляются автоматически.

При новом импорте D1 с другой SHA исходной книги необходимо заново экспортировать
справочные размеры и длины болтов и пересобрать приложение. До этого справочник
предыдущей книги не используется для завершённого расчёта. Импорт поддерживает
необязательный первый аргумент — путь к исходному XLSM, затем запускается сборка
компактного каталога (`npm run prebuild`). Исходная книга не редактируется.

Заданный формат кода не кодирует отдельный PN второго контура. При совпадении
кода и различающемся физическом исполнении API отклоняет обновление с 409,
вместо перезаписи чужой конфигурации; сохранённый состав доступен для сравнения.

Общий lint и полный TypeScript-check на момент реализации содержат ошибки
в прежнем коде подбора насосов, просмотра чертежей, спецификации, шкафов и
декларациях Cloudflare. Новые модули проходят ESLint. Production build и тесты
проверяются отдельно; несвязанные участки не рефакторились.

Результат итогового запуска: `npm test` — production build и 41 тест успешно.
Общий ESLint: 8 прежних ошибок и 1 предупреждение; ESLint новых модулей — без
ошибок. Полный `tsc --noEmit --incremental false` показывает 6 прежних ошибок
типизации; в новых модулях ошибок нет. Миграции проверены на отдельной SQLite-базе
в тестах; удалённая production D1 в рамках этой работы не изменялась.

## Исправление локальной ошибки 503 (10 сентября 2026)

В запущенной локальной D1 существовали только таблицы авторизации и проектов,
созданные прежним кодом. Журнал подтвердил `no such table: collectors` и
`no such table: catalog_imports`. После резервной копии в `.wrangler/backups`
применены миграции 0000 и 0005 через Wrangler с `--local` к
`frontend/.wrangler/state`. Проверка `PRAGMA quick_check` вернула `ok`, количество
пользователей и проектов сохранилось. Для удаления сохранённого сообщения
об ошибке в интерфейсе требуется повторная загрузка страницы.

Если аналогичная ситуация возникнет в другой локальной установке, сначала
проверьте существующие таблицы. Миграции создания уже существующих таблиц
повторно не запускаются. Для локальной базы без таблиц каталога и коллекторов,
после резервного копирования и production build, из папки `frontend`:

```powershell
node node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_burly_jackpot.sql
node node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0005_collectors.sql
```

Эти команды предназначены только для локальной D1. Удалённая production-база
не изменялась.
