# Локальное хранение полной версии
## Границы и переход
На Windows браузер использует прежний HTTP API и авторизацию Worker. Miniflare вызывает внутреннюю службу Node через service binding без отдельного HTTP-порта. Node владеет пулом PostgreSQL. Полный конфиг хранится в JSONB. D1 продолжает обслуживать пользователей, права, базовые значения и каталоги. Список проектов возвращает карточки, конфиг читается по одному ID.

Порядок переключения: копия SQLite → сверка перенесённых проектов → локальная проверка PostgreSQL и восстановления → запуск полной версии с новой базой. Данные профилей разработки и рабочего запуска размещают в разных каталогах и базах PostgreSQL. Код проекта не должен быть местом постоянного хранения локальных данных.

В четырёх самых крупных сохранённых конфигах 1 647 292, 1 325 086, 555 290 и 550 196 байт UTF-8. В первом спецификация занимает 971 987 байт, модель 472 639, настройки 148 150. Есть одинаковые вложенные снимки сборки вставки (~37 КБ). Полные снимки оставляем как свидетельство исходных цен, тарифов, состава и сварки. Каталог STEP и STL хранится отдельно от конфигов.

Критерии переключения: повторяемый импорт с исходными владельцами и ID, чтение после перезапуска, сохранение >2 МБ, идемпотентный повтор, защита от записи чужого проекта и гонки двух вкладок, восстановление ревизии и пробное восстановление базы и библиотеки. Ограничение по умолчанию — 10 000 000 байт UTF-8 на конфиг. Внешний доступ не требуется.

## Локальная установка на Windows

Команды выполняются в PowerShell из `E:\PumpStation_Calculator\frontend`. Для рабочего и испытательного профилей создайте разные базы, учётные записи и каталоги постоянных данных. Доступ к данным и резервным копиям ограничьте своей учётной записью Windows. Конфигурацию с паролями держите вне репозитория.

1. Установите PostgreSQL для Windows из [официального дистрибутива](https://www.postgresql.org/download/windows/). Выберите сервер и Command Line Tools, каталог кластера вне репозитория, например `E:\PumpStation_Data\postgres\data`. Укажите пароль администратора, порт 5432, в `postgresql.conf` задайте `listen_addresses = '127.0.0.1'`, в правилах локального TCP-подключения используйте SCRAM. Запустите локальную службу PostgreSQL. Добавьте её каталог `bin` в PATH текущего PowerShell.
2. Создайте владельца прикладной базы и базу. Для рабочего профиля повторите с другими именами. У прикладного пользователя достаточно прав владельца своей базы.

```powershell
createuser -h 127.0.0.1 -U postgres --pwprompt psc_dev
createdb -h 127.0.0.1 -U postgres -O psc_dev psc_dev
```

3. В каждом процессе используйте настройки своего профиля. В URL нужен процентно-кодированный пароль. Путь состояния Worker должен указывать на согласованную копию прежнего дерева Miniflare, включая локальную D1 с пользователями и каталогами. При переносе остановите писателей либо создайте резервную копию SQLite средствами SQLite. Не копируйте файл работающей базы без журнала WAL.

```powershell
$env:PROJECT_DATABASE_URL = 'postgresql://psc_dev:<password>@127.0.0.1:5432/psc_dev'
$env:PROJECT_STATE_DIR = 'E:\PumpStation_Data\development\state'
$env:PROJECT_MODEL_LIBRARY = 'E:\PumpStation_Data\development\model-assets'
$env:MODEL_CONVERTER_STATE = 'E:\PumpStation_Data\development\converter'
$env:PROJECT_LIMIT_BYTES = '10000000'
$env:PROJECT_AUTO_REVISIONS = '20'
npm ci
node scripts/migrate-local-projects.mjs '<путь к согласованной копии D1.sqlite>'
node scripts/publish-local-library.mjs 'E:\PumpStation_Calculator'
node scripts/migrate-local-converter.mjs '<путь к копии каталога старого конвертера>'
```

Перенос проектов и конвертера допускает повторный запуск. Миграция проектов сверяет исходную ревизию и владельца внутри одной транзакции. Публикация копирует уникальные STEP и STL, проверяет SHA-256 и записывает профили с единицами и портами. На этой библиотеке для отдельной копии нужно около 38 ГБ. Исходные модели из Git и Equipment остаются материалами для новой публикации.

4. Для подготовки новых STEP установите Python с поддерживаемым cadquery-ocp (на этом проекте обычно Python 3.13). Создайте окружение вне исходников, установите `services/model-converter/requirements.txt`. Задайте одинаковый случайный `MODEL_CONVERTER_TOKEN` длиной от 24 символов для приложения и конвертера. Запустите конвертер в отдельной консоли с теми же переменными.

```powershell
py -3.13 -m venv E:\PumpStation_Data\development\cad-env
& E:\PumpStation_Data\development\cad-env\Scripts\python.exe -m pip install -r services/model-converter/requirements.txt
$env:MODEL_CONVERTER_URL = 'http://127.0.0.1:8766'
& E:\PumpStation_Data\development\cad-env\Scripts\python.exe services/model-converter/server.py --host 127.0.0.1 --port 8766
```

5. Соберите полную версию. Для обновлений копируйте весь готовый `dist` в отдельную папку релиза под `frontend\work\releases\<версия>\dist`: Node находит пакет pg через `frontend\node_modules`. Постоянные данные располагаются отдельно от релиза.

```powershell
npm run build:full
node scripts/preview-full.mjs --build-dir dist --port 3108
```

В производственном запуске замените `dist` на путь к копии релиза. При обновлении сначала соберите другую папку, остановите старую версию и запустите новую с теми же настройками хранилища. PostgreSQL, схема, исходные STEP, опубликованные STL и конфигурации не пересоздаются при сборке. Для запуска после перезагрузки можно назначить локальные задачи Windows от учётной записи, имеющей права на эти каталоги. Сначала запускается PostgreSQL, затем конвертер и приложение. Оба HTTP-сервера слушают только loopback.

## Профиль запуска

`npm run start:local` читает `%LOCALAPPDATA%\PumpStationCalculator\full.json`.
Создайте его вне Git после настройки базы, каталога D1, библиотеки и Python.
Пример структуры; пути, пароль, токены и порт замените значениями своего профиля:

```json
{
  "PG_BIN": "C:\\Program Files\\PostgreSQL\\<версия>\\bin",
  "PG_DATA": "E:\\PumpStation_Data\\development\\postgres-data",
  "PG_PORT": 5432,
  "PROJECT_DATABASE_URL": "postgresql://psc_dev:<password>@127.0.0.1:5432/psc_dev",
  "PROJECT_STATE_DIR": "E:\\PumpStation_Data\\development\\state",
  "PROJECT_MODEL_LIBRARY": "E:\\PumpStation_Data\\development\\model-assets",
  "MODEL_CONVERTER_STATE": "E:\\PumpStation_Data\\development\\converter",
  "MODEL_CONVERTER_URL": "http://127.0.0.1:8766",
  "MODEL_CONVERTER_TOKEN": "<случайный секрет не короче 24 символов>",
  "CAD_PYTHON": "E:\\PumpStation_Data\\development\\cad-env\\Scripts\\python.exe",
  "buildDir": "work/releases/2026-11-01/dist",
  "port": 3000
}
```

Порт в `PROJECT_DATABASE_URL` должен совпадать с фактическим портом кластера.
Для CAD-экспорта дополнительно задайте `CAD_EXPORT_URL` и `CAD_EXPORT_TOKEN`
по [инструкции исполнителя](solidworks-export.md). Скрипт запускает PostgreSQL,
если кластер остановлен, затем скрытый процесс конвертера и приложение.
Занятые порты приложения или конвертера требуют проверки перед запуском второй
копии. Если службы уже работают отдельно, передайте окружение напрямую в
`node scripts/preview-full.mjs --build-dir <снимок>/dist --port 3000`.

Обновление: соберите full, создайте новый снимок, укажите его `buildDir`,
остановите старое приложение/конвертер и запустите профиль с прежними постоянными
каталогами. Пароль, токены, профили и данные в Git не добавляются.

## Сохранение, расчёт и очередь

Рабочее пространство запрашивает карточки по 25 без JSON. При открытии оно читает выбранную ревизию. Редактор ведёт отдельный черновик экземпляра вкладки в IndexedDB. Сервер проверяет владельца, роль, тарифы, размер конфигурации и исходную ревизию. Обновление строки проекта, запись снимка и квитанция уникального запроса идут в одной транзакции. Повтор операции с другими данными отклоняется. Восстановление выбранной версии создаёт новую.

В модели сохраняются версии каталога, адреса неизменяемых файлов, положение, поворот и ручные привязки. Отсутствующие модели используют существующее условное представление. Проект сохраняет исходные DN и PN, материалы, параметры насосов, снимки спецификации с ценами, сборки вставок и коллекторов, опубликованные версии базовых значений и идентификатор методики. Ревизия, перенесённая из прежней версии, может не иметь идентификатора методики. Загрузка снимка не меняет его цены. Изменение расчётных параметров или команда пересчёта использует доступные каталоги. Отметка времени явного пересчёта позволяет зафиксировать результат отдельной ревизией.

Исключение для текущего открытого проекта — целевое исправление КИП от 01.11.2026: старый преобразователь без модели/цены получает одно из двух согласованных ONI, очищаются предупреждения переходника/футорки, исправляется выбор реле напорной вставки. Остальные цены, расчётные снимки и параметры сохраняются. Эта коррекция выполняется после загрузки каталогов без общего пересчёта и сохраняется обычной новой ревизией; прежние ревизии и их экспорт остаются неизменными.

Массовый расчёт вставок по диапазону DN ставит проверенные входные данные и снимок каталога в очередь PostgreSQL. Одиночный DN рассчитывается в обычном запросе. Интерфейс ожидает результат задания. При изменении каталога выгрузка требует пересчёта. Сервис STEP хранит задания и контрольные суммы в схеме cad_worker. Обработчики разделяют один слот выполнения тяжёлой работы через advisory lock PostgreSQL. Статус доступен, пока идёт расчёт. После перезапуска берётся сохранённое задание. Для отдельного запуска вычислителя установите `PROJECT_WORKER_MODE=external` у приложения и запустите `node <релиз>/calculation-worker.mjs` отдельным процессом в окружении той же базы. Версии и формат проекта от размещения обработчика не зависят.

## Резервная копия и откат

Остановите процессы редактора, конвертера и публикации каталога. PostgreSQL продолжает работать. Для копии выберите **новую** папку на другом диске. Передайте все три пути состояния и URL одной базы.

```powershell
node scripts/local-storage-maintenance.mjs backup 'D:\PSC-backups\backup-001'
```

Скрипт сохраняет прикладные таблицы PostgreSQL в одном согласованном снимке, D1 (через SQLite VACUUM INTO), библиотеку и состояние конвертера. Файл backup.json записывается после завершения. Копия содержит рабочие проекты и сведения авторизации. В дополнение для всего кластера можно применять штатные pg_dump/pg_restore и резервирование Windows. Собственная копия охватывает только перечисленные прикладные таблицы. При расширении схемы обновите список таблиц и тест восстановления.

Для проверки создайте отдельную пустую базу и задайте новые, ещё не существующие каталоги PROJECT_STATE_DIR, PROJECT_MODEL_LIBRARY, MODEL_CONVERTER_STATE. Переключите PROJECT_DATABASE_URL на пустую базу, затем выполните:

```powershell
node scripts/local-storage-maintenance.mjs restore 'D:\PSC-backups\backup-001'
node scripts/preview-full.mjs --build-dir dist --port 3109
```

При восстановлении сверяются количество строк, контрольные суммы таблиц и опубликованных исходников и сеток. В случае частичной ошибки используйте новые пустые каталоги для повторной попытки. Запустите конвертер из восстановленного профиля и откройте станцию со ссылками на подготовленные модели.

**Откат после переключения.** Остановите запись, сделайте полную копию PostgreSQL, D1 и файлов, затем выполните `node scripts/local-storage-maintenance.mjs export '<новый каталог>'`. Каждая текущая станция будет отдельным JSON, в index.json сохранены ID и владелец. Запускайте прежнюю сборку только на отдельной копии старой D1. Восстанавливайте изменения нужного владельца из экспортов после проверки. Прежняя сборка не способна принять JSON больше её лимита. Для таких проектов и истории сохраните PostgreSQL и полный архив до возврата на совместимую сборку. Никогда не заменяйте новую базу устаревшим файлом SQLite.

## Оставшиеся зависимости и порядок миграции

| Область | Источник в этой версии | Следующий отдельный этап |
|---|---|---|
| Проекты, история, указатели на модели | PostgreSQL. Внутренний service binding, без отдельного публичного порта | Один владелец записи — служба проектов |
| Аккаунты, уровни доступа, сессии, одноразовые токены | D1 через auth-server и users-server | Перенести с прежними ID и проверками ролей, затем общие внешние ключи |
| Тарифы и опубликованные базовые значения | D1 через base-values-server | Импорт неизменяемых версий и сверка применённых снимков |
| Каталог компонентов, расчётные вставки, коллекторы, шкафы | D1 и подготовленные справочники | Перенос связанных таблиц по группам, сверка состава и цены до переключения |
| Ассистент | Читает собственный проект из PostgreSQL, справочные данные из D1 | Перенос ограничений и остальных запросов вместе с таблицами |
| CAD | Файлы в постоянном каталоге, метаданные и очередь в PostgreSQL | Для переноса обработчика предоставить доступ к тем же неизменяемым файлам и базе |
| Исполнение веб-приложения | Локальный Node + Miniflare, Worker сохраняет существующие HTTP API и авторизацию | Замена среды выполнения возможна отдельно от миграции таблиц |

## Профиль на этом ПК

Перед запуском `preview-full.mjs` проверяет SHA-256 сеток, на которые напрямую
ссылаются сборки КИП, баков и концевиков, и копирует недостающие STL из
`public/model-assets` в `PROJECT_MODEL_LIBRARY`. Используется
`scripts/local-runtime-models.mjs`. Существующая сетка с другой контрольной
суммой не перезаписывается: запуск завершается с ошибкой. Закреплённые версии
каталога и проекты не изменяются. Для уже запущенного экземпляра можно выполнить
`node scripts/local-runtime-models.mjs` с тем же `PROJECT_MODEL_LIBRARY`;
внутренний ASSETS binding увидит новые файлы без перезапуска сервера.

Рабочий профиль full использует PostgreSQL 18 на `127.0.0.1:55432`, базу `psc_full`, файлы в `E:\PumpStation_Data\full`. В этой папке находятся `postgres`, `state` (локальная D1), `model-assets` и `converter`. Неизменяемые файлы исходных моделей могут использовать общие блоки диска через NTFS hard links. Каталоги версий, настройки, базы и файлы, которые меняются при работе, у рабочего и испытательного экземпляров отдельные.

Сохранённые параметры запуска доступны учётной записи Windows в `%LOCALAPPDATA%\PumpStationCalculator\full.json`. Файл содержит пароли и токен конвертера. В профильной папке также хранится пароль администратора переносимой PostgreSQL. Их не включают в Git. Приложение подключается к собственной базе под ролью без прав администратора кластера.

Из `frontend` запуск выполняется командой:

```powershell
.\scripts\start-local.ps1
```

Скрипт поднимает имеющийся локальный кластер, конвертер и полную сборку по адресу `http://127.0.0.1:3000/`. При обновлении остановите экземпляр, соберите и скопируйте новый релиз в новую папку, обновите `buildDir` в профиле и запустите скрипт. Для резервирования параметры хранилища можно загрузить в текущую консоль без вывода их значений:

```powershell
$cfg = Get-Content -Raw -LiteralPath "$env:LOCALAPPDATA\PumpStationCalculator\full.json" | ConvertFrom-Json
foreach ($k in 'PROJECT_DATABASE_URL','PROJECT_STATE_DIR','PROJECT_MODEL_LIBRARY','MODEL_CONVERTER_STATE') {
    [Environment]::SetEnvironmentVariable($k, [string]$cfg.$k, 'Process')
}
node scripts/local-storage-maintenance.mjs backup 'D:\PSC-backups\full-001'
```

Для восстановления задайте другие пути и URL отдельной пустой базы согласно разделу выше. В испытании архив первой стадии с проектами дополнялся отдельной копией ещё не перенесённой SQLite старого конвертера и его STL. После завершения миграции включайте MODEL_CONVERTER_STATE в каждую копию, чтобы в неё попадали и модели, подготовленные пользователями.

Нагрузочная проверка параллельного чтения одного крупного конфига из локального API не характеризует время отрисовки 3D на компьютерах пользователей.
